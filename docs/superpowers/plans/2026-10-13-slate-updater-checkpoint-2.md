# Slate updater Checkpoint 2 implementation plan

> Execute the approved checkpoint with test-driven development and independent spec/quality review. Do not commit, install, generate keys, configure production endpoints, or change release files.

**Goal:** Add a Rust-owned, installation-disabled updater and a compact sidebar experience.

**Architecture:** A managed controller owns one cancellable operation, update offers, verified bytes, and revisioned snapshots. The official updater 2.13.3 Rust adapter checks trusted configuration and calls download-only signature verification. No installation API is exposed or called. Configuration remains absent; real checks fail closed without a key/endpoint, while dependency-injected tests exercise the complete state machine. The frontend subscribes before reading a snapshot, rejects stale revisions, and renders existing-design-system controls without touching library state.

**Tech stack:** Pinned Tauri v2, Rust, existing futures/semver dependencies, React, existing Tauri IPC/events and Slate UI components.

**Approved transport alignment:** The updater uses its supported `native-tls`, `zip`, and `system-proxy` features with default features disabled. On Windows HTTPS uses SChannel; certificate validation, Minisign verification, and required signed-version binding remain enabled. Verify x64/ARM64 builds and absence of the updater's ring/clang dependency before continuing.

**Pinned SDK initialization boundary:** In updater 2.13.3 the updater constructor is private. When trusted configuration is present, the public `Plugin::initialize` method initializes the official plugin's Rust state with sanitized configuration. The temporary plugin is then dropped without registering it in the plugin store, so its JavaScript install handlers are not exposed. This lifecycle boundary was independently reviewed against the pinned SDK and must be rechecked on future SDK upgrades. No SDK initialization happens when configuration is absent.

## Approved safety and behavior

- Preserve all seven approved Checkpoint 1 changes, primary main, release hashes, and the extension archive.
- Do not fabricate a key or bypass verification. A missing configuration is an explicit unconfigured state. SDK registration must not prevent startup when configuration is absent.
- Only main receives status events and five commands: `get_update_status`, `check_for_updates`, `download_update`, `cancel_update`, `dismiss_update`. No plugin-wide, install, process, filesystem, or frontend HTTP permission is granted.
- Snapshots include `revision`, `phase`, `currentVersion`, `availableVersion`, `downloadedBytes`, `totalBytes`, `dismissed`, `error`, and `installationEnabled: false`.
- Phases: `unconfigured`, `idle`, `checking`, `up_to_date`, `available`, `downloading`, `verifying`, `ready`, `error`.
- Later hides the notice for this process/session; manual Check for Updates restores access. No persistent preferences or database schema changes.
- Update Now downloads only. Main Create/Edit, destructive confirmation, and pending library mutations disable its UI action. Ready has a disabled restart/install control and an explicit checkpoint explanation. Because no installer execution exists, launcher drafts and concurrent capture cannot be lost to installation either.
- Startup checks are spawned asynchronously and never show/focus a window. Missing configuration makes no request. No automatic downloads or installs.
- Cancellation aborts the future and invalidates the operation generation. Late callbacks/results cannot affect a new operation. Errors are fixed, content-free messages; retry preserves the ability to check/download.
