# Technical Architecture

## Recommended stack

### Windows desktop application
- Tauri
- React
- TypeScript
- Vite
- Tailwind CSS
- shadcn/ui where useful
- SQLite

### Browser extension
- Chrome Extension Manifest V3
- TypeScript
- React only where UI requires it

### Monorepo
Recommended:

```text
/
  apps/
    desktop/
    extension/
  packages/
    shared/
  docs/
```

A package manager workspace such as pnpm is preferred.

## Core architecture

```text
Browser
  ↓
Chrome/Edge Extension
  ↓
Local communication bridge
  ↓
Tauri desktop application
  ↓
SQLite
```

SQLite is the source of truth.

There is no cloud database in the MVP.

## Extension-to-desktop communication

Preferred long-term approach:
- Chrome Native Messaging

Acceptable MVP alternative:
- localhost HTTP service bound only to `127.0.0.1`

If using localhost:
- never bind to `0.0.0.0`
- use a random or fixed high local port
- validate requests
- use a local secret/token generated by the desktop app
- do not expose the service to the LAN

If Native Messaging is straightforward enough, prefer it.

## Data model

Suggested SQLite table:

```sql
CREATE TABLE clips (
  id TEXT PRIMARY KEY,
  content TEXT NOT NULL,
  content_type TEXT NOT NULL DEFAULT 'text',
  title TEXT,
  source_app TEXT,
  source_url TEXT,
  source_page_title TEXT,
  is_pinned INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

Add indexes for:
- created_at
- is_pinned

Add SQLite FTS later when basic search works.

## Search progression

### Phase 1
Simple case-insensitive substring search.

### Phase 2
SQLite FTS5.

### Later
Semantic search using local or optional remote embeddings.

Do not start with vector search.

## Shared types

The desktop and extension should share TypeScript types where practical.

Example:

```ts
export interface ClipInput {
  content: string;
  contentType: "text" | "code" | "prompt" | "link";
  title?: string;
  sourceApp?: string;
  sourceUrl?: string;
  sourcePageTitle?: string;
}
```

## Privacy architecture

Default:
- all clip content stored locally
- no telemetry containing clip content
- no analytics SDK that reads saved content
- no account
- no backend dependency

If diagnostics are added later, never include clip contents.

## Future sync architecture

Cloud sync is explicitly NOT part of the MVP.

If added later:

```text
SQLite
  ↓
optional sync engine
  ↓
client-side encryption
  ↓
remote encrypted storage
```

The local database must remain usable if sync is disabled or unavailable.

## Security rules

Treat captured text as sensitive user data.

Never:
- upload clips automatically
- log full clip content to console in production
- include clip content in crash reports
- expose the local bridge publicly
- execute saved code
- render unsanitized HTML from captured content


## Platform strategy

Windows is the first supported desktop platform.

macOS support is planned for a later release.

Shared product logic must remain platform-independent wherever practical.

OS-specific behavior must be isolated behind platform-specific modules or interfaces.

Examples of platform-specific behavior:
- global shortcuts
- quick-launch window behavior
- native messaging registration
- startup/login behavior
- tray/menu-bar integration
- active-app paste/injection
- OS permissions

Do not implement macOS functionality during the Windows MVP unless required to preserve a clean abstraction.

The goal is:
- one shared React UI
- one shared clip/data model
- one shared SQLite schema
- one shared browser extension where possible
- small platform-specific Tauri/native layers for Windows and macOS
